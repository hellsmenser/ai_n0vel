# План завершения Ren'Py-клиента

Статус документа: утверждённое направление работ; Этапы 0–4 реализованы локально к 2026-10-19, следующий — Этап 5.

## Цель

Довести Ren'Py-клиент до состояния, в котором JSON-сцены воспроизводятся детерминированно, сохранение и загрузка возвращают игрока в правильную точку, rollback и история работают на уровне отдельных реплик, а стандартный интерфейс заменён единым кастомным GUI.

План относится только к клиенту и его границе получения сцен. Реализация Python AI Gateway рассматривается отдельно.

## Архитектурное решение

JSON остаётся исполняемым форматом сцены. Генерировать динамические `.rpy` не требуется.

Исходный проигрыватель выполнял всю сцену внутри одного Python statement. Ren'Py сохраняет позицию на границе statement, поэтому загрузка или rollback из середины такого вызова повторно запускали часть сцены. Он заменён пошаговой state machine: одна итерация Ren'Py label-loop выполняет одно JSON-действие, а cursor фиксирует текущее незавершённое действие.

## Этап 1. Контракт сцены и состояние проигрывателя

**Статус: завершён 2026-10-17.**

- Введён строгий контракт `schema_version: 1`: неизвестные поля и действия, дубли ключей, неподдерживаемые версии и отсутствующие ресурсы отклоняются до вызова handlers.
- Зафиксированы лимиты недоверенного JSON: 1 MiB, глубина 20, 10 000 узлов, 500 действий и ограниченные строки/персонажи.
- Действия согласованы с handlers и объявленными ресурсами. `animate.effect` использует объект `shake`; `music` намеренно не входит в v1 до появления handler и аудиоресурсов.
- Создан сохраняемый `PlaybackState` со следующими данными:
  - `scene_id`;
  - `schema_version`;
  - `content_hash`;
  - неизменяемый snapshot текущей сцены;
  - `step_index`;
  - состояние ветвления и переменные сцены;
  - фаза проигрывания и последняя структурированная ошибка.
- Snapshot нормализуется, копируется, получает канонический SHA-256 и проверяется после save/load; сохраняемое значение объявлено через `default`.
- Mongo-клиенты, файлы, потоки, handler-функции и временные объекты персонажей в state не помещаются.
- Поддержана ограниченная миграция legacy v0; Python demo-generator и task id синхронизированы с v1.
- Оркестратор проверяет сцену до публикации, пишет её атомарно и переводит задачу в `error`, а не `done`, при невалидном результате или ошибке записи.

Критерий завершения выполнен: валидная сцена получает стабильный snapshot, а невалидная не запускает handlers, возвращает структурированную ошибку и не блокирует очередь. Полная матрица: JSON parse `24/24`, lint `PASS`, native testcases `29/29`, `overall_passed=true`; Python-оркестратор — `20/20` unit tests.

## Этап 2. Пошаговый JSON-проигрыватель

**Статус: реализован локально 2026-10-18.**

- Заменить Python-цикл по всему `dialogue` на Ren'Py label loop.
- Выполнять ровно одно действие по текущему `step_index` за итерацию.
- Увеличивать курсор только после успешного завершения действия.
- Оставить по одному взаимодействию на реплику, паузу или выбор.
- Запретить handlers скрыто менять Ren'Py control flow через `renpy.jump()`; handlers должны возвращать результат `continue`, `scene_end`, `goto` или `error`.
- Не выполнять сетевые операции внутри проигрывания сцены.
- Не проглатывать неизвестные actions и исключения.

Критерий завершения: save/load в любой контрольной точке возвращает игрока на ту же реплику без перезапуска всей сцены.

Проверено: save на второй реплике не повторяет первую (`1/2/2` после load), rollback на 1/3/10 реплик и через границу сцены восстанавливает cursor, `goto` завершает state и сохраняет branch trace, а ошибка handler не сдвигает cursor. `pause` имеет отдельный hard checkpoint.

## Этап 3. Save/load, rollback и история

**Статус: реализован локально 2026-10-18.**

- Добавить `after_load` для проверки состояния и безопасной остановки несовместимого проигрывания. Автомиграция `PlaybackState` v1 → v2 намеренно не выполняется: старая модель не гарантирует корректный cursor, поэтому несовместимый save отклоняется fail-closed до handler.
- Разрешить продолжение уже полученной сцены без доступной MongoDB.
- Использовать стандартное добавление истории через `renpy.say`.
- Удалить прямое ручное создание `HistoryEntry` и изменение `_history_list`.
- Через `config.history_callbacks` добавлять к записи `scene_id`, `step_index` и `speaker_id`.
- При наличии rollback identifier разрешить переход к доступной реплике из окна истории.
- Через `config.save_json_callbacks` добавить в save metadata название сцены, номер реплики и версию контракта.
- Заменить удаление Mongo-задачи при воспроизведении на идемпотентное подтверждение `consumed`; чистку вынести за пределы rollbackable-клиента.

Критерии завершения:

- загрузка возвращает на сохранённую реплику;
- история не теряет и не дублирует строки после load/rollback;
- rollback работает минимум на 10 последовательных реплик и через границу сцены в пределах rollback log;
- загрузка полученной сцены работает при недоступной MongoDB.

Проверено: History получает ровно одну штатную запись на реплику и контекст `scene_id/step_index/speaker_id`; ранние записи не дублируются после load, доступная запись History выполняет `RollbackToIdentifier`, save-slot JSON содержит только инертные метаданные, а очередь подтверждает `done → consumed` без удаления задачи. Snapshot сцены продолжает выполняться без повторного чтения MongoDB или файла.

Итоговая матрица Этапов 0–3 от 2026-10-18: JSON fixtures `36/36`, Ren'Py 8.3.4 lint `PASS`, native testcases `53/53`, `overall_passed=true`, без свежих error diagnostics. Python-оркестратор: `20/20` unit tests.

## Этап 4. Клиентская инфраструктура и ошибки

**Статус: реализован локально 2026-10-19.**

- Выделить интерфейс `SceneProvider`, скрывающий источник сцены: MongoDB, fixture или будущий API.
- Добавить состояния ожидания, временной потери соединения, повреждённой сцены, отсутствующего ресурса и неподдерживаемого действия.
- Добавить управляемые действия `Повторить` и `В главное меню`.
- Настроить короткие сетевые timeout, чтобы polling не замораживал интерфейс.
- Делать autosave только в стабильной точке на границе сцены.

Критерий завершения: внешняя ошибка не приводит к молчаливому пропуску действия или зависанию клиента.

Проверено: `SceneProvider` скрывает Mongo/file/fixture-источники, а live client хранится вне save-state. Ошибки poll/prepare/playback/acknowledge имеют структурированный код и Retry/Main Menu; недоступный MongoDB port приводит к `provider_offline` менее чем за 8 секунд. Poll/refill ограничены числом remote-операций и сохраняют traversal cursor между вызовами. Ack retry не переигрывает сцену; playback retry сохраняет cursor и разрешён только для безопасных терминальных действий. Блокирующий autosave выполняется отдельным statement после completed playback и подтверждённого ack; настоящая загрузка autosave восстанавливает стабильную `boundary`. Повреждённый `SceneSessionState` отклоняется fail-closed.

Итоговая матрица Этапов 0–4 от 2026-10-19: JSON fixtures `37/37`, Ren'Py 8.3.4 lint `PASS`, native testcases `62/62`, `overall_passed=true`, без свежих error diagnostics. Python-оркестратор: `20/20` unit tests.

Оставшийся компромисс: прототип выполняет короткие синхронные MongoDB-вызовы на Ren'Py interaction thread. Timeouts и bounded work ограничивают зависание, но production-граница должна перейти на локальный адаптер/API или асинхронную доставку событий. Реальный Compose/MongoDB end-to-end в этот этап не входил.

## Этап 5. Кастомный GUI

Визуальная работа может идти параллельно с техническими этапами. Окончательного `PlaybackState` требуют только динамические элементы статусов, ошибок, истории и metadata сохранений.

Порядок:

1. Подготовить 2–3 полноэкранных концепта и выбрать направление.
2. Зафиксировать дизайн-систему: палитру, шрифты с кириллицей, типографику, отступы, состояния элементов и набор иконок.
3. Создать графические ассеты для 1920×1080 с использованием `Frame`/9-slice там, где элементы должны масштабироваться.
4. Оформить главное меню, dialogue box, namebox, quick menu, choices, save/load, history, preferences, confirm, ожидание генерации и error overlay.
5. Не запекать динамический текст в изображения.
6. Проверить desktop и small/touch variants.

Критерий завершения: все пользовательские экраны используют одну дизайн-систему, сохраняют стандартные Ren'Py actions и корректно показывают состояния проигрывателя.
